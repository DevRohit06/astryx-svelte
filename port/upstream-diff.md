# Upstream diff — a six-axis audit against Astryx 0.3.0

Dated **2026-08-11**, against upstream's clone at `reference/astryx-upstream/` and the published
`@astryxdesign/*` 0.3.0 tarballs. Six agents ran in parallel over disjoint axes: packaging, published
API, CLI, themes/CSS, tests, and core runtime modules.

This is a point-in-time audit, not a living document. Anything here that stays open belongs in
`todo.md`; anything about how a unit was built belongs in `port/ledger/`. Its purpose is the thing
neither of those files could give: a **measured** answer to "where has this port drifted, in both
directions."

Every finding traces to a file read or a command run. Where a number contradicts one this repo has
published, the recomputation and its method are stated so the disagreement can be settled rather than
believed.

**Status legend** — `NEW` not recorded anywhere · `RECORDED` already tracked (line cited) ·
`DELIBERATE` intentional and documented · `FIXED` fixed in this pass.

## 1. Packaging and distribution

### 1.1 `main` was absent from every package — FIXED

Upstream sets it on all of theirs (`"main": "./dist/index.js"` on core, `"./dist/source.js"` on a
theme). We set it on none of ten.

With `exports` present, Node and every modern bundler ignore `main` entirely — which is exactly why
this survived a release and a publint gate. Anything that does **not** understand `exports` could not
resolve `@astryx-svelte/core` or any theme at all.

Added to core and all eight themes. The CLI correctly still has none: upstream's has none either.

### 1.2 The unported upstream packages were scoped out for a false reason — NEW

`todo.md:3618-3626` explains not porting `@astryxdesign/build` as "build tooling, not a
consumer-facing package" whose job "may already be done by this repo's own theme build scripts". Both
halves are wrong. It is `private: false`, versioned 0.3.0 in lockstep with core, sits in
`.changeset/config.json`'s `fixed` group, and publishes four bundler integrations — `./babel`,
`./postcss`, `./vite`, `./next`. Our `@astryx-svelte/core/vite` re-implemented one of the four.

The inverse is also true and more useful: `lab`, `charts`, `vega` and `richtext` are all
`private: true`, stranded at 0.1.x, outside the fixed group, and each says of itself that it is
"published to npm only under the `@canary` dist-tag; never released as a stable version". **Not
porting them is not a parity gap — it matches upstream's own release policy.** That should be
recorded as settled rather than carried as debt.

### 1.3 Smaller packaging gaps — NEW

- No tarball carries a `CHANGELOG.md`; upstream's `files` ships one per package. (npm auto-packs
  README and LICENSE, never CHANGELOG.)
- Theme packages omit `module`, `types`, `sideEffects` and `keywords`. Upstream sets
  `sideEffects: false` on theirs — worth confirming against our `theme.css` before copying, since a
  blanket `false` can license a bundler to drop a stylesheet import.
- `./api` is the only CLI subpath we publish with no `types`. Upstream generates the whole `.d.mts`
  tree from `scripts/sync-api-types.mjs`, wired as `prepack`; we have neither.

## 2. Themes, CSS and tokens

### 2.1 The pre-built stylesheet was a missing port, not a limitation — FIXED

Upstream publishes `./astryx.css` → `dist/astryx.css`, generated by `scripts/build-css.mjs`. We
shipped no such thing, and `packages/core/README.md` explained the absence as intrinsic: *"Astryx's
own package ships pre-built CSS… This one cannot."*

That was wrong, and it made every consumer configure a compiler for a failure mode that renders
correct markup with no styling and never throws.

Upstream's script is now ported at `packages/core/scripts/build-css.mjs`, wired into `prepack`, and
exported as `./astryx.css`. It copies upstream's output format deliberately — one `@layer
astryx-base`, and `processStylexRules(rules, false)`, so priority is `:not(#\#)` specificity padding
rather than `@layer priority1…9`. A consumer ordering layers around Astryx orders around **upstream's
layer name**.

Two deliberate differences, both in `scripts/lib/collect-stylex-rules.mjs`: it compiles from
`src/lib` rather than a build output, and a module that fails to compile is fatal. Upstream warns and
carries on, which turns a broken module into a stylesheet silently missing its rules.

**Verified, not asserted.** A third oracle, `compare-upstream-css.mjs`, diffs the result against
upstream's published sheet on every test run: **1,463 shared atomic classes, zero differing rules**;
27 marker-scoped rules paired after blinding their path-derived hashes; 10 named skips.

It is not redundant with `compare-upstream-classes.mjs`. That one reads modules *statically* and
cannot see inside a `stylex.create` function style — there are 54, and the blindness is documented.
The CSS oracle compares what the compiler emitted, where a function style is just another rule. It
found finding 3 on its first run.

Mutation-checked in both directions: deleting Avatar's RTL branch produced
`missing rule upstream ships: .xqgnvz5:is([dir="rtl"] *){transform:translate(-50%,50%)}`; a skip that
no longer applies is reported and fails the run.

### 2.2 The declared layer order omitted the layers the compiler emits — FIXED

`base.css` declared `@layer reset, astryx-base, astryx-theme, product;`. But compiling this package
yourself produces `@layer priority1 … priority9`, and **layer order is order of first appearance** —
so nine layers nobody named landed *after* `product`, inverting the cascade.

Every consequence is silent: a theme's overrides stop applying to components, and app CSS loses to
component CSS it should beat.

The complete order already existed — but only in `docs/src/app.html`, where no consumer could benefit
from it. `base.css` now names `priority1…16` between `astryx-base` and `astryx-theme`.

Verified in a real build rather than reasoned about, and the first attempt was wrong: the docs bundle
was rebuilt against a stale `dist/`, and showed no change. After rebuilding core, the emitted CSS
carries `@layer astryx-base,priority1,…,priority16;` at byte **13,394**, ahead of `astryx-theme` at
13,580 and `product` at 156,743. Correct order, from the `base.css` import alone.

Note this cannot be fixed by matching upstream's `useCSSLayers: false` instead: the plugin would then
emit **unlayered** rules, which beat every layered rule and would defeat theming outright. Upstream
escapes that only by wrapping at build time, which a consumer's build does not do.

**Still open:** four documented recipes (`migration.doc.mjs:135,151`,
`styling-libraries.doc.mjs:179`, `styling.doc.mjs:146`) declare a layer order *before* importing
`base.css`. A consumer following them establishes order first, so the priority names still land last.
Those four samples need the priority layers, and the docs registry regenerating.

### 2.3 The theme `.` export means something different on each side — NEW

Upstream: `.` = the **source** theme (`defineTheme(...)`, extensible, and what drives `Theme.tsx`'s
injection branch); `./built` = the compiled artifact. Ours: `.` = the compiled artifact; `./built`
throws `ERR_PACKAGE_PATH_NOT_EXPORTED`; `./tokens` is ours alone.

`src/<name>-theme.ts` ships inside the tarball but appears in no export, so **there is no published
path to derive a theme from upstream's** — which is the entire point of upstream's default entry.
Affects all eight theme packages; unrecorded.

### 2.4 No `.stylex` token subpath — RECORDED (`todo.md:5518`)

Upstream ships `./theme/tokens` and `./theme/tokens.stylex`; the second is how a consumer authors
their own StyleX against Astryx tokens. `dist/styles/tokens.stylex.js` **already ships in our
tarball** — only the closed `exports` map blocks it.

This was measured, not assumed: importing our `colorVars` through the `./theme` barrel makes the
StyleX Babel plugin fail with *"Could not resolve the path to the imported file… `.stylex.js` or
`.stylex.ts` extension"*, while a direct path compiles. Two export keys close it.

### 2.5 Also absent — NEW

`tailwind-theme.css` (9.2 kB, ~120 `@theme inline` mappings) and any `*.css.d.ts`, so
`import '…/base.css'` from TypeScript is a TS2307.

**Clean:** theme content is 2,418 / 2,436 declarations with 0 mismatches and 0 invented, the
remainder being the 18 documented `color-scheme` rules; token defaults are byte-identical (24 consts,
184 keys); `reset.css` → `base.css` has 0 value mismatches; `liquid-glass` is correctly labelled as
the port's own addition in all five places it is published.

## 3. CSS correctness

### 3.1 Avatar's status dot was mispositioned in RTL — FIXED

Found by the new CSS oracle on its first run.

`avatar.stylex.ts` used a physical `right`, matching upstream **0.2.0**. Upstream 0.3.0 moved to
`insetInlineEnd` and mirrored the `translate` that pushes the dot onto the circle's edge
(`translate(50%, 50%)` in LTR, `translate(-50%, 50%)` in RTL). Ours kept the old version, under a
comment arguing for it.

This is precisely the class of bug `compare-upstream-classes.mjs` cannot reach: `statusPosition` is a
`stylex.create` **function style**, opaque to a static reader. The class oracle reported 0 mismatches
throughout.

Fixed to match upstream 0.3.0; no test depended on the old behaviour.

## 6. Tests

### 6.1 "434 upstream cases have no counterpart" is wrong — the number is 577 — NEW

This is published in `CHANGELOG.md` and `todo.md`.

The 434 came from auditing only upstream files **whose filename had no match here**. That method is
structurally blind to a suite which *has* a counterpart file and drops a third of its cases.
Recomputed: **294** absent (26 files) + **283** short inside ported suites = **577**. Counting the 7
N/A `.doc.mjs`/build-tooling suites and 4 deliberately-declined ones puts it at 688. The non-theme gap
alone is 436 — already past the published total.

Method: a case is an `it`/`test` at line start, not inside a comment, with `.each` arrays/tables and
`describe.each` expanded. Line-anchoring is required or a string like `'…pressed inside it (APG
menu-button)'` counts as a case. Known floor: loop-generated cases count as 1, giving ~1.8% undercount
on our own core (4,976 static vs 5,066 reported); the bias is symmetric, so the deltas hold.

### 6.2 Four ported suites contradict their own headers — NEW

The repo's contract is that upstream suites are ported case-for-case and **any dropped case is named
in the file with its reason**. These do not:

1. **`top-nav-menu.svelte.test.ts` — 4 of 12**, header says "all 4… nothing dropped." The eight
   absent are the entire APG keyboard model: roving tabindex, Arrow navigation, wrap, typeahead,
   Enter/Escape, and the `role="dialog"` negative. Highest risk in the repo — stateful focus
   behaviour actively asserted as covered.
2. **`slider.svelte.test.ts` — 32 of 46**, header says "nothing dropped, nothing added." 13 unnamed
   drops on a pointer-capture/keyboard control whose interaction path already diverges from
   upstream's.
3. **`plain-date.test.ts` — 4 drops, no header at all.** All four are `plainDateFormat` shape cases,
   the function behind this repo's own documented runtime-locale hazard.
4. **`form-and-metadata.svelte.test.ts`** — claims FieldStatus is "upstream's 31"; it is 34. Its
   FormLayout block is 12 of 17 with only 3 snapshots named.

Two more contradict their bodies numerically but harmlessly: `chat-composer-input` ("44 here", file
has 51) and `time-input` ("37 here", file has 39). The other 21 count disagreements all name their
drops properly.

### 6.3 Highest-risk unported suites

`Chat/ChatComposer` (5) and `ChatComposerDrawer` (3) — still unported, and the precedent that already
shipped a live bug. `Stack`+`StackItem`+`HStack`+`VStack` (65). `Grid` (36). `theme/tokens` (22) and
`themingTargets` (13), with nothing else covering token resolution. `Heading` (23), `Kbd` (15), the
`i18n` e2e pair (10), `sharedResizeObserver` (6).

Also: the CLI's exit-code/error-envelope/JSON-contract cluster (~65 cases) is the **machine-readable
agent contract** and is entirely uncovered — it passes empirically today, but nothing pins it across a
Commander bump, which has already bitten twice at 12→14. And `apps/docsite`'s 19 suites / 303 cases
have zero counterpart and zero record.

**Clean:** all 15 beyond-upstream files correctly declare their justification at the top.

## 7. Core runtime modules

### 7.1 The i18n provider recomputes locale direction on every context read — NEW

`internationalization-provider.svelte:70-75` puts `dir ?? getLocaleDirection(locale)` **inside** the
context getter, and `useTranslator` calls that getter once per `t()`. Measured 3.98 µs/call against
0.04 µs for the object literal alone over 200k iterations — roughly 4 ms per render pass on a page
with 1,000 translated strings. Upstream computes it once per provider render and memoises.

Fix: `const direction = $derived(dir ?? getLocaleDirection(locale))`, referenced from the getter.
That stays live across a runtime locale swap, which is the reason the current comment gives for
computing it in place.

### 7.2 The "19 hooks" claim is stale — there are 22 — NEW

Upstream's barrel publishes 22, at both the clone and the published `dist/hooks/index.d.ts`. All 22
**are** ported, so only the prose is wrong — but it ships inside `dist/*.d.ts` (`hooks/index.ts:4`,
`internal/optimistic.svelte.ts:8`, `internal/theme-mode.svelte.ts:9`) as well as `CHANGELOG.md:78`
and `todo.md:122`.

### 7.3 Smaller — NEW

`useSize` drops upstream's `<T extends string>` generic, so a consumer's own size union cannot be
typed (nothing internal regresses: all 18 upstream call sites are `useSize(sizeProp, 'md')`).
`useKeyboardHint` requires an options getter with a required `id`, so upstream's own no-argument call
does not compile — the cause is recorded as a class at `todo.md:3433`, just not for this hook.

### 7.4 The vendored catalogs have no mechanical guard — NEW

The claim checks out: `en.json` is 250/250 keys byte-identical in the same key order, and
`fr-FR`/`pseudo` are byte-identical too. But **nothing in `pnpm -r test` re-verifies any of it**, and
`todo.md:769-772` records the exact failure mode already happening once — 31 keys behind, with
nothing reporting it — and closing it with a habit rather than a check. An ~8-line server test gates
it.

**Verified clean:** every shared pure module is transcription-identical under a comment- and
import-stripped token diff (all of `utils/`, `resolve.ts`, `computeOverflow`, `themeProps`,
`parseStyleKey`); literal-set diffs across the seven largest hooks show no divergent string or number;
all 22 hooks' options and defaults match; all five contexts store **getters** with upstream's
defaults.

## What was changed in this pass

All verified, all in `packages/core` unless noted.

- `scripts/build-css.mjs` + `scripts/lib/collect-stylex-rules.mjs` — upstream's generator, ported.
  Wired into `prepack`; `dist/astryx.css` confirmed present in the packed tarball.
- `scripts/compile-dist-stylex.mjs` — compiles `dist/**/*.stylex.js` so the stylesheet stands alone.
  Shipping `astryx.css` was not sufficient on its own: `stylex.create` **throws** at runtime rather
  than degrading, so the sheet without a compiler produced a crash, not an unstyled page. Compiles
  each module under its **source** identity, because StyleX hashes `defineVars` companion classes
  from the module path — the first run mismatched 26 classes against `astryx.css` for exactly that
  reason, and the script now asserts the two agree.
  Verified as a consumer: a Vite app with no StyleX plugin, driven in headless Chromium, renders an
  Avatar at `border-radius: 9999px`, `36×36`, `inline-flex`.
- `package.json` — a `source` export condition on all nine non-CSS subpaths, so the tree-shaken
  route survives. Both routes are alive, as upstream has them.
- **This was a breaking delivery change.** A precompiled `dist` gives a consumer's StyleX plugin
  nothing to compile. The docs site hit it exactly — CSS fell from ~250 kB to 161 kB with no error —
  and now imports `astryx.css`; across its prerendered pages every atomic class in the markup
  resolves in the CSS (365/365, 284/284, 353/353).
- `packages/cli/api/doctor/doctor.mjs` — the StyleX check accepts either route. Without this it would
  have told every correctly configured route-1 project that its components render unstyled. Two
  cases added and mutation-checked.
- `scripts/compare-upstream-css.mjs` — the third fidelity oracle. Mutation-checked in both
  directions. Wired into `test` as `test:css`.
- `package.json` — `main`, the `./astryx.css` export, `build:css` and `test:css`.
- Eight theme manifests — `main`.
- `src/lib/components/avatar/avatar.stylex.ts` — the RTL fix.
- `src/lib/styles/base.css` — the full layer order.
- `README.md` — the styling section rewritten around two routes; the false "cannot ship pre-built
  CSS" claim and the stale "no `astryx.css`" bullet removed.
- `docs/src/app.html`, `CLAUDE.md`, `CHANGELOG.md`, `todo.md` — records brought in line.

`pnpm -r lint` clean, `svelte-check` 0 errors across 2,066 files, all three oracles green, and
`check-publish` reports all ten packages fit to publish.
